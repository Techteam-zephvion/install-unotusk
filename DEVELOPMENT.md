# UNOTUSK — Local Development Guide

For a new developer who just got this workspace and needs to get the whole stack running locally, understand what's where, and iterate on changes without re-reading the whole install pipeline.

## 1. Repo map — what's in each folder

This directory (`install-unotusk`) is its own git repo. Every subdirectory below is a **separate, independently-owned git repo** (gitlinks, not submodules) — each shows up here for local dev convenience only.

| Folder | What it is | Language | Remote |
|---|---|---|---|
| `US/` | Auth Service — GitHub OAuth login, sessions, gRPC `AuthService` (ExchangeRef, ValidateToken, GetCurrentUser), admin pairing, employee cert issuance | Rust (axum + tonic) | `Anikethanshetty/Unotusk-Auth-server` |
| `UPS/` | Company Server — licensing, degraded mode, gRPC `ClientService`, admin pairing | Rust (axum + tonic) | `Anikethanshetty/Unotusk-Company-Server` |
| `AI-PIE/` | Intelligence engine — ingestion, spec/report generation (`/api/spec/generate`, `/api/report/generate`), ontology | Python (FastAPI) | `Techteam-zephvion/AI-PIE` |
| `UP/` | Platform — cloud-only (Render + Neon), license issuance, org/project registry, JWKS push receiver | Rust (axum) | `Techteam-zephvion/UP` |
| `UCA/` | Employee desktop client ("Zephvion") — login, project workspace, Ask/spec-generation | TypeScript/Next.js + Tauri v2 | `Techteam-zephvion/Unotusk` |
| `UAC/` | Admin console desktop client — UPS/US pairing, employee directory, role presets, project grants | TypeScript/Next.js + Tauri v2 | `Techteam-zephvion/UnotuskAdminConsole` |
| `installer/` | The real customer-facing installer (wizard, cert generation, docker-compose template, CLI) | Bash | lives in this repo |
| `scripts/`, root `install.sh` | An **older, separate** local-dev-only install path — not what customers get, has its own bugs, don't confuse with `installer/` | Bash | lives in this repo |

Each of `US/UPS/AI-PIE/UP/UCA/UAC` has its own `CLAUDE.md`/`AGENTS.md` — read it before working inside that directory.

## 2. Architecture in one picture

```
Internet → Cloudflare DNS → platform.unotusk.com (marketing/docs only)
                                      │
                    UP (Render + Neon) — cloud-only, never in local compose
                                      ▲
                           outbound license heartbeat + JWKS push
                                      │
──────────── Customer machine (docker compose) ────────────
  US (3100 HTTP / 50052 gRPC / 8444 admin / 8446 pairing-code)
       │
  UPS (50051 gRPC / 8443 admin / 8447 pairing-code)
       │
  AI-PIE (8000, own mTLS dev CA)
       │
  Postgres, Qdrant, Phoenix, Redis (internal only, not published)

UCA / UAC run as native desktop apps on employee/admin laptops,
connecting to US/UPS/AI-PIE over the network (not in docker compose).
```

## 3. First-time setup — run the real stack locally

```bash
cd /home/devils/PRO/Unotusk
cp .env.example .env                      # POSTGRES_PASSWORD, PLATFORM_URL, PLATFORM_LICENSE_KEY
cp US/.env.example US/.env
cp UPS/.env.example UPS/.env
cp AI-PIE/.env.example AI-PIE/.env
```

Certs are generated by the installer, not by hand — either run the real installer end-to-end (`installer/install.sh`, wraps `installer/lib/certificates.sh` + `configuration.sh` + `docker.sh`), or if you already have a working `/opt/unotusk` install, certs live there under `US/certs/`, `UPS/certs/`, `AI-PIE/certs/dev/`.

```bash
docker compose up -d
docker compose ps      # everything healthy within ~60s
```

`UP` (Platform) is **not** in this compose file by design — cloud/Render-only. Point local dev at the real deployed instance (see §6) rather than trying to run it locally.

## 4. Running UCA / UAC as dev builds

Both are Next.js + Tauri v2 apps with an identical dev workflow.

```bash
cd UCA        # or UAC
npm install
npm run dev          # Next.js dev server only, port 3005 (UCA) — for pure frontend iteration
# or, for the real desktop app with hot reload:
npx tauri dev
```

`npx tauri dev` builds the Rust side once, then hot-reloads the frontend. For a full release build (what actually gets installed):

```bash
npx tauri build
# outputs:
#   src-tauri/target/release/bundle/deb/*.deb
#   src-tauri/target/release/bundle/rpm/*.rpm
#   src-tauri/target/release/bundle/appimage/*.AppImage
```

Install locally: `sudo dpkg -i src-tauri/target/release/bundle/deb/*.deb` (replaces the existing install; the local account/keychain data persists across reinstalls since it's stored separately from the app binary).

### Running with debug logs (essential for diagnosing login/network issues)

```bash
DEBUG_FLOW=1 RUST_LOG=debug /usr/bin/zephvion > /tmp/zephvion.log 2>&1 &
```

- `DEBUG_FLOW=1` — UCA-specific flag gating verbose flow logs (NFR-7: keeps secrets out of default logs)
- `RUST_LOG=debug` — full `tracing`/`reqwest`/`rustls` debug output, including TLS handshake detail

**Gotcha:** config (`/etc/unotusk/client.env`) is only read once at process startup. If you edit that file, you must fully quit and relaunch the app (`pkill -9 -f <binary>` then relaunch) — a window close alone may not be enough, and a *second* launch attempt while an old process is still alive will silently do nothing.

## 5. Rebuilding a backend service (US / UPS / AI-PIE) without a full reinstall

```bash
cd US   # or UPS
cargo build --release --bin auth-server   # or company-server — fast correctness check first
docker build -t <service>-local:debug .
docker tag <service>-local:debug ghcr.io/<real-image-name>:latest
cd /opt/unotusk
sudo docker compose up -d --no-deps --force-recreate --pull never <service>
```

**`--pull never` is not optional.** Without it, compose silently re-pulls the real GHCR image and clobbers your local build. Verify the swap took:

```bash
docker inspect unotusk-<service>-1 --format '{{.Image}}'
docker inspect <service>-local:debug --format '{{.Id}}'
# these two must match
```

## 6. `/etc/unotusk/client.env` — what it's for and what commonly goes wrong

This file is what UCA (and eventually UAC) read at startup to find US/UPS/AI-PIE/Platform. It's generated by `installer/lib/configuration.sh`'s `write_client_env()`. Known failure modes discovered the hard way — check this file first whenever login works but something downstream doesn't:

| Symptom | Cause | Fix |
|---|---|---|
| Login itself fails, generic "Sign-in failed" | `CLIENT_CRT`/`CLIENT_KEY` unset — US's gRPC listener requires *any* valid client cert, even to call `ExchangeRef` | Needs a bootstrap `uca-client` cert signed by the shared mesh CA (`US/certs/ca.crt`) — see `certificates.sh`'s "UCA bootstrap client cert" section |
| `ca_cert_len=0` in debug logs, `UnknownIssuer` on the server's own cert | `CA_CERT` path in `client.env` doesn't actually exist on disk | `cp US/certs/ca.crt /etc/unotusk/ca.crt` |
| Project list fails with "Can't reach the server" right after a successful login | `PLATFORM_BASE_URL` defaults to a placeholder domain (`platform.unotusk.com`), not the real Render deployment | Set `PLATFORM_BASE_URL=https://unotusk-platform-service.onrender.com` |
| Platform returns 503 `"auth service unavailable"` | UPS's own `PLATFORM_URL` (in `UPS/.env`, **not** the root `.env**) also points at the placeholder domain — its JWKS push has been silently failing | Fix `PLATFORM_URL` in `UPS/.env`, recreate the `ups` container |
| JWKS push still 401s after fixing the URL | `JWKS_PUSH_SECRET` in `UPS/.env` doesn't match the value configured on the live Render `unotusk-platform-service` | Generate a new shared secret, set it in **both** places, redeploy Render, recreate `ups` |
| "Ask" / spec generation fails, TLS handshake succeeds but empty reply | `UPS_BASE_URL` points at UPS's own port 8443 (its *admin* mTLS listener) instead of AI-PIE's port 8000 — confusingly named, but Ask always targets AI-PIE, never UPS | `UPS_BASE_URL=https://<host>:8000`, plus `UPS_CA_CERT`/`UPS_CLIENT_CRT`/`UPS_CLIENT_KEY` pointing at `AI-PIE/certs/dev/{ca.pem,client.pem,client.key}` |

All of the above are now fixed at the source in `installer/lib/configuration.sh` and `installer/lib/certificates.sh` — a fresh install shouldn't hit any of them. This table exists for diagnosing an **existing** install that predates the fix, or for understanding what `write_client_env()` is actually doing and why.

## 7. Port reference

| Port | Service | Notes |
|---|---|---|
| 3100 | US — OAuth HTTP (`/auth/login`, `/auth/callback`, `/healthz`, `/.well-known/jwks.json`) | published; container-internal port is 3000 |
| 50052 | US — gRPC `AuthService` (mTLS, mandatory client cert) | |
| 8444 | US — admin pairing listener (mTLS, for UAC) | |
| 8446 | US — pairing-code redemption (server-auth-only TLS) | new, replaces manual PEM paste |
| 50051 | UPS — gRPC `ClientService` (mTLS) | |
| 8443 | UPS — admin pairing listener (mTLS, for UAC) | **not** what UCA's "Ask" should hit |
| 8447 | UPS — pairing-code redemption | |
| 8000 | AI-PIE — spec/report generation (own mTLS dev CA) | what UCA's "Ask" actually hits |

## 8. Generating a UAC pairing code (replaces manual PEM paste)

```bash
unotusk pair us    # prints a code valid 10 min, redeemable once — for "Connect Auth Service"
unotusk pair ups   # same, for "Pair with your UPS instance"
```

Under the hood: `docker exec unotusk-<service>-1 curl -sf -X POST http://127.0.0.1:<3000|8080>/internal/pairing-code` — loopback-gated, only callable from inside the container itself.

## 9. Where logs live

- **US / UPS / AI-PIE**: `docker logs unotusk-<service>-1`
- **UCA/UAC (installed, GUI-launched)**: no persistent log file by default — run the binary directly from a terminal with `RUST_LOG=debug` (see §4) to see anything
- **Installer itself**: `$INSTALL_DIR/logs/` (typically `/opt/unotusk/logs/`)
